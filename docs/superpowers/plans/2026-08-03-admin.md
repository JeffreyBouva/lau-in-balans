# Laura als super admin — Implementation Plan

**Goal:** Laura is de eigenaar van het product en moet altijd álles kunnen zien, ook de
klanten van een andere coach. Het datamodel blijft multi-coach (`clients.coach_id`, gezet
door `verzilver_code` op basis van de eigenaar van de invite-code); daar komt één
admin-vlag bovenop.

**Branch:** `dashboard-v2`

---

## Wat er wijzigt

**`supabase/migrations/20260803120000_admin.sql`** (nieuw)

1. `coaches.is_admin boolean not null default false` + comment.
2. De demo-Laura (`laura@demo.lauinbalans.nl`) wordt admin. Bea bewust niet: zij is de
   RLS-isolatie-fixture.
3. `public.is_admin()` — sql, stable, security definer, `search_path = ''`; execute
   ingetrokken voor public/anon, verleend aan authenticated.
4. `public.is_coach_of(uuid)` — zelfde signature/opties als in de hardening-migratie,
   body wordt `public.is_admin() or exists (...)`. Hiermee erven de zeventien policies
   die deze functie gebruiken (messages, food_logs, flags, ai_profile_versions,
   coach_notes, weekly_sessions, ai_usage) plus de RPC `ai_gebruik_deze_maand` de
   admin-tak in één keer.
5. De vier policies die direct op `coach_id` matchen krijgen `or public.is_admin()`:
   `coach_leest_klanten` en `coach_wijzigt_klanten` (clients), `coach_leest_eigen_codes`
   en `coach_trekt_code_in` (invite_codes).

Klant-policies blijven ongemoeid. `is_admin()` is voor een klant per definitie false (geen
`coaches`-rij), en op `public.coaches` bestaat geen insert- of update-policy — de vlag is
dus alleen via de service role of SQL te zetten, nooit door een gebruiker zelf.

**`scripts/seed.mjs`** — Laura `is_admin: true`, Bea expliciet `is_admin: false`.

**`supabase/functions/prompt-preview/index.ts`** en
**`supabase/functions/sessie-voorstellen/index.ts`** — deze twee doen hun coach-check met
de service role (dus buiten RLS om) en moeten daarom zelf admin-bewust worden. Nieuw: eerst
de `coaches`-rij van de beller ophalen (geen rij → 403, dat is geen coach), dan bij
`is_admin` alleen checken dát de klant bestaat en anders de bestaande
`coach_id`-check. Verder blijven beide functies identiek.

**`tests/rls/admin.test.ts`** (nieuw, 13 tests) — wegwerp-fixtures: een admin-coach, een
gewone coach mét klant, een derde gewone coach zonder klanten. Dekt: `is_admin()` per rol,
"niemand promoveert zichzelf", de admin op alle `is_coach_of`-tabellen + clients +
invite_codes + de RPC, de isolatie van een gewone coach (de regressietest), en dat de
klantkant onveranderd is.

**`tests/rls/rls.test.ts`** — één aanpassing die de push nodig heeft: "Laura ziet alle zes
klanten" telde exact zes rijen. Als admin ziet Laura óók de wegwerp-klanten van de suites
die parallel draaien, dus die test zou meteen ná `supabase db push` rood worden. Nu pint
hij dat haar eigen zes klanten allemaal zichtbaar zijn (de isolatiekant staat bij Bea, de
admin-kant in `admin.test.ts`). Groen zowel vóór als ná de push.

## Jeffrey-stappen

**Volgorde is dwingend: eerst pushen (stap 1), dan pas deployen (stap 3).** De nieuwe
edge-function-code selecteert `coaches.is_admin`; staat die kolom er nog niet, dan geeft
die query een fout en antwoorden beide functies met `503 tijdelijk niet beschikbaar`.
Andersom (push zonder deploy) is ongevaarlijk: de oude functiecode draait gewoon door met
de strikte `coach_id`-check — Laura ziet dan in de preview/voorstellen alleen haar eigen
klanten, de rest van het dashboard werkt wél al admin-breed.

### 1. Migratie pushen

```bash
supabase db push
```

Verwacht: `Applying migration 20260803120000_admin.sql...` gevolgd door
`Finished supabase db push.` Staan er nog oudere migraties open, dan gaan die in dezelfde
run mee — dat is prima.

Foutbetekenis:

- `column "is_admin" of relation "coaches" already exists` → de migratie is al eens gedraaid;
  controleer met `select id, naam, is_admin from public.coaches;` in de SQL-editor.
- `policy "coach_leest_klanten" for table "clients" does not exist` → er ontbreekt een
  eerdere migratie; push die eerst (de `drop policy` in stap 5 van de migratie verwacht de
  policies uit `rls.sql`, `hardening.sql` en `fase5_dashboard.sql`).

### 2. RLS-tests draaien

```bash
npx vitest run tests/rls/admin.test.ts
```

Verwacht: **13 passed** (`Test Files 1 passed`). Alles groen.

Foutbetekenis:

- `PGRST202 ... public.is_admin` of `PGRST204 ... 'is_admin' column` → stap 1 is niet
  gelukt, of PostgREST heeft z'n schema-cache nog niet ververst (wacht een halve minuut en
  draai opnieuw).
- Een test in "isolatie blijft intact" die rood wordt is **ernstig**: dan ziet een gewone
  coach de klant van een ander. Niet deployen, eerst melden.
- Let op de GoTrue-ratelimit: draai niet twee volledige RLS-runs kort na elkaar, houd
  ~5 minuten tussenruimte.

### 3. Edge functions deployen

```bash
supabase functions deploy prompt-preview
```

```bash
supabase functions deploy sessie-voorstellen
```

Verwacht per commando: `Deployed Functions on project jzovciuubkwvbwxphamf: <naam>`.
De admin-check zit in de code, er zijn geen nieuwe secrets of config-wijzigingen nodig.

Foutbetekenis: `403 Forbidden` bij het openen van de prompt-preview in het dashboard voor
een klant van een andere coach → Laura's `is_admin` staat niet op true (zie stap 4).

### 4. Controleren dat Laura admin is

```sql
select c.naam, c.is_admin, u.email
  from public.coaches c join auth.users u on u.id = c.id;
```

Verwacht: Laura `is_admin = true`, Bea `false`. De migratie promoveert alleen de
demo-Laura (`laura@demo.lauinbalans.nl`). Draait de seed opnieuw, dan zet die de vlag ook
meteen goed.

### 5. Een échte coach admin maken

Voor een coach die niet uit de demo-seed komt (bijvoorbeeld Laura's productie-account):
zoek eerst het uuid op met de query uit stap 4 en zet dan de vlag.

```sql
update public.coaches set is_admin = true where id = '<uuid van de coach>';
```

Terugdraaien gaat net zo, met `false`. De vlag werkt direct — er hoeft niets gedeployd of
opnieuw ingelogd te worden.
